# Folder Tree Selection Highlight

`FolderTreeRow.rowContent` (Detail Panel's recursive subfolder tree) applied `.background(isSelected ? Color.accentColor.opacity(0.15) : .clear, ...)` directly to its `HStack`, with no `.frame(maxWidth: .infinity, alignment: .leading)` first. Unlike `DriveRowView` (`FolderFirstPanelView.swift`) and `BigFolderRowView` (`FolderSecondPanelView.swift`), which both explicitly frame to full width before their content, this row relied on implicit width propagation from the ancestor `VStack`/`ScrollView` chain plus an internal `Spacer()`. Inside a recursively-nested tree (each depth level re-wraps in its own `VStack`), that implicit propagation is unreliable — the `HStack` (and therefore its `.background`) can size to its intrinsic content width instead of the full row width, making the selection highlight invisible or clipped to a sliver next to the folder name instead of spanning the row.

Fix: add `.frame(maxWidth: .infinity, alignment: .leading)` to the `HStack` before `.padding(.leading:)` and `.background(...)`, matching the convention already established by `DriveRowView`/`BigFolderRowView`. This guarantees the background (and the `contentShape`/tap target) always spans the full available row width regardless of recursion depth.

See also [List selection hit testing](/Users/Workspaces/AI-SpecCoding/Source/DeskUtils/Views/FolderManagerView/.memory/List-Selection-Hit-Testing.md) — same underlying principle (full-width frame required for reliable hit-testing/highlight), but that note covers `List(selection:)`-based rows in the first two panels; this tree uses manual `onTapGesture` + a selected-folder binding instead of `List` selection, so the missing frame here breaks the highlight's visible extent rather than its hit-testing.
